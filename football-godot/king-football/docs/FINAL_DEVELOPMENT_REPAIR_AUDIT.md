# Final development repair audit

Base: `origin/main` @ `c22ec6c` (PR #77), branch `repair/development-ecosystem`.
Method: source read in this session, plus the existing suites run headless (Godot 4.7.1). Old audit documents were not used as evidence.
Status legend: **FIXED** (code + test in this branch) / **OPEN** (confirmed, not fixed yet) / **UNVERIFIED** (suspected, not yet proven) / **NOT AUDITED**.

## Confirmed findings

### F1 — Calendar catch-up silently dropped weeks — Critical — FIXED
* `DevelopmentEngine.sync` jumped `first` forward and counted `skipped_weeks` when `owed > 60`, then set `last_week = absolute_week` (old `development_engine.gd:44-49`).
* `TrainingSystem.sync_to_calendar` set `calendar_week = absolute_week` *before* processing only `min(owed, 60)` weeks (old `training_system.gd:37-38`): the remainder was lost without any record.
* `YouthDevelopment.sync` and `ScoutingSystem.sync_to_calendar` had the same cap-and-forget pattern.
* Fix: the persisted "last processed week" now advances one week at a time, only over weeks really processed. `DevConfig.CATCH_UP_BATCH_WEEKS` (60) bounds the work of ONE call; the remainder stays queued (`pending_weeks(...)`) and the next call resumes it. `last_week` / `calendar_week` are already saved, so a queue survives save / load. `skipped_weeks` is kept only as a legacy field from old saves and is never increased.
* Test: `player_development_validation` `_test_catch_up_queue` — 10 / 60 / 100 / 200-week jumps (first batch size, queued remainder, exactly-once totals, repeated sync adds nothing), save / load in the middle of a queue, training and youth 200-week jumps. The previous assertion that *pinned the dropping behaviour* (`skipped_weeks == 140`) was replaced, not weakened.
* Remaining caveat: after a jump larger than one batch the queue drains over the following sync calls (each career tick), not inside one call.

### F2 — No stored detailed attributes — High — PARTLY FIXED (storage, compatibility, plans, sessions, coaching lead; UI views still open)
* `PlayerData.ATTRIBUTES` has seven broad attributes (`player_data.gd:16`). They feed `get_overall`, the match engine, training, plans and saves.
* `AttributeDetail` (`attribute_detail.gd`) exposes 18 "detailed" names, but they are **derived** from the seven (parent average + a fixed per-player offset), are not stored, cannot be trained, and are not the requested list (no Finishing/Shot Power/Long Shots/Volleys/Penalties/Heading, Short/Long Passing, Crossing, Curve, Marking, Interceptions, Jumping, Strength, Concentration, Anticipation, Decisions, Work Rate, Aggression, Teamwork, keeper Reflexes/Diving/Handling/Kicking/1v1 ...).
* Consequence: development plans and training sessions can only target the seven broad attributes (`DevelopmentEngine._first_team_week` iterates `plan["weights"]` over `PlayerData.ATTRIBUTES`; `get_attribute` returns 0 for anything else).
* Implemented (step 2): `scripts/data/detailed_attributes.gd` — 40 stored, trainable detailed attributes (technical / physical / mental / goalkeeping), each with ONE broad parent. Storage is lazy (`PlayerData.detail` is empty until a detailed attribute is first trained, so existing players / packs / saves are unchanged and need no migration). Training a detailed attribute adds 1 to it and 1/Z of a point to its parent (Z = details sharing the parent), so the broad attribute the match engine reads tracks the average; the potential cap is checked on the broad rise. A broad change by any other route (legacy training, ageing, lifecycle) moves the details under it by the same amount via the `PlayerData` setters. Corrupt stored data is sanitised on load. `AttributeDetail` (the older read-only database view) reports a stored value when present.
* Evidence: `tests/detailed_attributes_validation` (47 checks: catalog completeness, no double counting for every position, untouched players unchanged, materialising keeps the overall, 1/Z accounting, potential and 99 limits, goalkeeper-only details, propagation, JSON round trip, old-save and corrupt-save loading, validation). A numeric bug found by these tests (seven additions of 1/7 summing to 0.99999994 and missing a broad point) is fixed with `DetailedAttributes.EPSILON`.
* Step 3 (plans): templates, roles and sessions now target detailed attributes (`development_plans.gd`, `dev_config.gd`). Templates for striker / winger / midfielder / centre-back / goalkeeper are exactly the specified lists. Custom plans take up to five attributes. Plans written before this change are upgraded in place on first processing (clock, cycles, history, intensity kept; attribute / custom plans keep their broad targets). Each detailed attribute has a leading coaching department (`DevConfig.lead_department`), specialisations favour their own attributes (`SPEC_DETAILS`), and the tactical coach's share is no longer applied twice to attributes he already leads. The academy accepts detailed training focuses. 40 `DEV_ATTR_*` translation keys (en / de / ar) were added. Evidence: `player_development_validation` 227 / 0 (26 new checks), plus regression runs listed below. A bug found on the way: `lead_department` returned "tactical" for unlisted details instead of the parent's department (fixed).
* Still open for F2 / step 3: the Development Hub / Individual Development / Analytics screens still show the broad bars (only the custom-plan editor and labels were adapted); the academy training screen still offers the seven broad categories; position conversion and the historical per-attribute view are not re-verified in the UI.

### F3 — Several coaching factors multiplied into the academy `dev_bonus` — High — FIXED
`career_state.gd:123` multiplies, for the managed club's academy: manager style x facilities x `staff.youth_factor()` (old `StaffTeam`) x progress x `training.development_factor()` x `YouthDevelopment.coach_factor` (academy's own coach quality) x `coaching.academy_factor()` (new `CoachingStaff`). `group_bonus` (`:126`) then multiplies the group's share again inside `TrainingSystem`.
Three different "coach quality" sources are stacked. Whether that is intended compounding or double counting has not been measured; the requirement forbids duplicate bonuses, so it must be resolved (one source of truth per effect) and covered by a test.

### F4 — Two staff systems coexisted — Medium — FIXED (legacy roles bridged; the old staff list keeps assistant / doctor / chief scout / youth coach)
`StaffTeam.BRIDGED` bridges only `fitness_coach` and `goalkeeping_coach` into `CoachingStaff` (`staff_team.gd:16`, `DevelopmentEngine._import_legacy`). `StaffTeam.youth_factor()` and the academy's own `staff` dictionary remain independent sources (see F3).

## Proposed approach for F2 (to be confirmed)
Keep the seven broad attributes as the match-engine inputs. Store detailed attributes per player as a dictionary of *trained deltas* on top of the existing deterministic derived base (so old players start with identical values and the match engine is unchanged at migration time). Training a detailed attribute adds weighted fractional progress to its parent broad attribute(s) once (no double counting). Plans / sessions target detailed names; the seven broad names stay valid for old plans.

## Steps 5-6 (coaching unification, youth coaching) — implemented
* F3: `CareerState` no longer multiplies `StaffTeam.youth_factor` x `YouthDevelopment.coach_factor` x `CoachingStaff.academy_factor`. `DevelopmentEngine.best_academy_coaching` takes the BEST of the three, which describe the same thing (they were stacked up to three times). Tested: result equals the maximum and is below the product; weaker sources never lower a stronger one.
* F4: `StaffTeam.BRIDGED` now includes `first_team_coach` -> the tactical department (it had no effect at all before: `coaching_factor()` had no caller). A legacy head coach is imported once as the tactical coach and leaves the old list (wage not paid twice; exactly one coach per department afterwards). `goalkeeper_factor()` / `coaching_factor()` (no callers) were removed; the goalkeeping coach acts through `CoachingStaff` (goalkeeping department). The old staff screen lists assistant / doctor / chief scout / youth coach only.
* Youth matches (`YouthDevelopment._grow`) picked a RANDOM broad attribute and used only the academy coach. With the new hooks (`DevelopmentEngine.youth_hooks`) a league match trains the attribute of the prospect's development plan, boosted by the BEST of the academy coach and the specialist coach of the prospect's age group (`attribute_multiplier(attr, "youth", group)`); coaches assigned to another group do not help. Without hooks the old behaviour is unchanged. Tested for U15 / U17 / U19 independently and for plan-following growth (no other detailed or broad attribute moves).
* Coach recruitment, negotiation, contracts, wages, renewal, dismissal, vacancies, capacity, wage budget, progression and specialisation were already implemented and tested (`player_development_validation`, e.g. hire / budget / renewal / dismissal / progression checks); they were not rewritten.
* Not done: a separate "youth development" department (youth coaching is modelled by assigning department coaches to age groups, which the architecture already supports); loan growth and mentor growth are not boosted by the specialist coach (they happen outside the academy).
* Regression after steps 5-6: `player_development_validation` 242 / 0; `detailed_attributes` 47 / 0; `phaseT5` 69 / 0; `phaseT6` 67 / 0; `phaseT10` 127 / 0; `phaseT12` 58 / 0; `phase6_integration` 105 / 0; `career_flow` 79 / 0; `localization` 100 / 0.
